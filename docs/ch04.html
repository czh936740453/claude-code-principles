04 · 工具系统

理解「工具 = 函数 + 说明」：模型怎么知道能用什么工具、怎么调用、结果怎么回来。

本章目标　理解「工具 = 函数 + 说明」：模型怎么知道能用什么工具、怎么调用、结果怎么回来。前置依赖　建议先读第 3 章。

04 /工具 = 函数 + 说明

对 Claude Code 来说，一个工具就是三样东西：名字（怎么称呼它）、说明（什么时候用它、怎么用）、函数（真正干活的代码）。模型看到的不是代码，而是「说明书」——一段 JSON：

模型读到这份「说明书」，就知道：有个工具叫 read_file，用来读文件，需要传一个 path 参数。它不直接调用函数，它只是「请求」调用。

04 /工具注册表：只能调用登记过的

程序内部维护一张「工具名 → 函数」的表（叫注册表）。模型发来 tool_use 请求后，程序查表、校验参数、执行、返回结果。查不到就报错，绝不静默。这就是为什么模型永远无法调用你没给它的工具。

04 /调用协议：tool_use 和 tool_result

模型和程序之间的「工具对话」只有两种消息，像一个接力棒：

  1. 模型发出 tool_use模型说：「我要调用 read_file，参数是 path=notes.txt」。
  2. 程序执行工具程序在本地真实执行，拿到结果。
  3. 程序回填 tool_result把结果作为一条新消息放回上下文。
  4. 模型继续模型看到结果，决定下一步：继续调用工具，还是结束。

04 /内置工具长什么样

工具作用风险等级
Bash执行 shell 命令（跑测试、装依赖、操作文件）高
Read读取文件内容低
Write写入 / 覆盖文件中

Grep / Glob搜索文本 / 按模式找文件低
WebFetch抓取网页内容低

04 /权限拦在哪一步

注意流程里的闸门：模型发出 tool_use 请求后，程序不会立刻执行，而是先过一道权限检查（第 5 章详细讲）。只有被允许的工具调用才会真正执行——这是安全设计的核心。

1. 模型直接调用工具函数吗？

模型只发 tool_use 请求；程序负责查注册表、校验、执行、回填结果。 回看：调用协议

2. 「工具注册表」的作用是？

注册表是「工具名 → 函数」的映射，模型无法调用没登记的工具。 回看：注册表

3. 模型拿到工具时，实际「看到」的是什么？

模型看到的是 JSON Schema 说明书，不是实现代码；执行由程序在本地完成。 回看：工具 = 函数 + 说明
本章小结
  • 工具 = 名字 + 说明书（JSON Schema）+ 函数。
  • 模型只发 tool_use 请求，程序查注册表执行并回填 tool_result。
  • 工具调用前要先过权限闸门。
✗ 误区：以为模型直接调用工具函数
✓ 真相：模型只发 tool_use 请求；程序查注册表、校验参数、执行、回填结果。
✗ 误区：以为工具越多越好
✓ 真相：每个工具都要占上下文 token；工具应该精简、说明清晰，够用就好。
✗ 误区：以为模型能看到工具的源码实现
✓ 真相：模型看到的是 JSON Schema 说明书（名字 + 说明 + 参数格式），不是实现代码。
